# Validation Quickstart: Publications Library

This guide describes the end-to-end checks the implementation must support. It does not authorize
production deployment or the deferred R2 custom-domain change.

## Prerequisites

- Hugo Extended version used by the existing site
- Node.js version used by repository automation
- Approved publication fixtures conforming to [data-model.md](data-model.md)
- A staging publications service and configured staging asset base URL

## Public-site validation

```powershell
hugo --minify --gc
node --test tests/publications-schema.test.mjs
hugo server --buildDrafts --disableFastRender
```

Expected outcomes:

1. The build completes without warnings caused by publication templates or content.
2. Publications appears as a hierarchical menu and is usable by pointer, touch, and keyboard.
3. The landing page exposes all three series, Major articles, and Books.
4. Query and filters update results and the URL; clearing filters restores the collection.
5. With JavaScript disabled, server-rendered collections and document actions remain available.
6. Draft, future-dated, and `catalogue: false` fixtures are absent from public HTML/JSON.
7. The constitution remains linked from About Us but does not appear in the catalogue.

## Accessibility and responsive review

- Check 320 px, 768 px, and 1280 px layouts.
- Traverse the entire header, filters, cards, and document actions using keyboard only.
- Confirm focus is visible and disclosure state is announced.
- Run the project's automated HTML/accessibility scan, then manually review menu focus order,
  filter labelling, error/empty states, and PDF action text.

## Migration validation

The committed migration ledger uses the deterministic JSON subset of YAML 1.2 so it remains
dependency-free and can still be loaded from Hugo's `data/` directory. Generate a fresh read-only
report (the command prints JSON and never downloads PDFs or changes the ledger):

```powershell
node scripts/inventory-publications.mjs
node scripts/inventory-publications.mjs --write-ledger
```

The first command is the safe default; the explicit second form refreshes the tracked ledger while
preserving any previously reviewed disposition by URL. Review its diff before committing.

After editorial and rights review updates `rights_status`, `disposition`, and approved record/asset
metadata in `data/publication-migration.yml`, preview the conversion plan, then opt in to creating new
page bundles:

```powershell
node scripts/migrate-publications.mjs
node scripts/migrate-publications.mjs --write
```

The writer requires `rights_status: approved`, validates the complete publication contract, confines
output to the expected collection, and uses exclusive file creation so it cannot overwrite existing
content. Compare:

- source URL count by category/series;
- migrated/redirected/excluded/missing totals;
- duplicate asset and publication IDs;
- every alias target;
- a sample PDF and cover from every series/year represented.

The totals must reconcile to 100% of the reviewed inventory before enabling the menu in production.

## Cross-repository scenario

1. Sign in as a publication editor.
2. Upload a valid pilot PDF and create a draft magazine record.
3. Preview it and confirm it is absent from the published site build.
4. Publish it, run the Hugo build, and open the detail page/document.
5. Edit the same record in two sessions and verify the stale session receives a conflict.
6. Repeat upload and mutation attempts as an unauthorized user and verify no change.
7. Point the build at a replacement asset base URL and verify links change without content edits.

## Cost baseline and guardrails

- **Owner**: public-site maintainer, reviewed immediately after migration and 30 days after launch,
  then quarterly.
- **Build budget**: the publications catalogue remains generated by Hugo with no database or paid
  search service. A 5,000-card local filter must complete in under one second in the automated test.
- **Delivery budget**: HTML/JSON remain on the existing static host. PDFs live in the shared cms-media R2
  bucket and use a configurable base URL; the custom domain remains intentionally deferred.
- **Request budget**: catalogue filtering makes zero API requests. One PDF click should produce one
  cacheable asset request; investigate if R2 Class B operations exceed 10,000/month or egress crosses
  the current free allowance.
- **Storage budget**: alert when stored PDFs exceed 5 GiB or monthly growth exceeds 500 MiB, then
  review duplicates, retention, and whether the expected R2 paid tier remains cheaper than alternatives.
- **Exit strategy**: publication metadata is portable Git content, PDFs have stable object keys, and
  changing storage requires only copying objects plus updating `publication_asset_base_url`.

## Implementation verification record

Verified locally on 2026-10-30:

- `node --test tests/*.test.mjs`: 15 tests passed, including schema/visibility, migration safeguards,
  stable navigation, catalogue filtering, and detail-action contracts.
- The 5,000-record filtering fixture completed in 26 ms on the verification host, below the one-second
  target.
- `hugo --minify --gc`: passed without warnings; the final fixture-free production build generated 74
  pages. A temporary valid publication bundle was also built and inspected at its catalogue,
  collection, detail, metadata, and missing-R2-base states, then removed.
- The read-only live inventory found 94 unique legacy PDF links. Every item is recorded as
  `review_required`/`pending`; none is authorized for upload or publication yet.
- Real R2 object migration, editorial/rights disposition, staging cross-repository validation, and
  the intentionally deferred R2 custom domain remain outstanding external steps.
